# Per-Rule Anomaly Status Files

This directory contains audit and reproducibility CSV files that map every rule in each of the five stateful firewalls to its specific structural anomalies and security findings. These files are programmatically generated by `code/rule_anomaly_status.py` using:

* `Real-Dataset/unified/<vendor>.csv` — The normalized rule set.
* `results/anomalies.jsonl` — All raw pairwise and single-rule findings (1,387 total findings).
* `results/scored_anomalies.jsonl` — Risk scores and exposure/blast-radius metrics computed for each finding.

## Column Guide

### Rule Specification Columns (Imported from the Unified Model)
* `vendor`: The firewall manufacturer/product name.
* `rule_id` / `rule_name`: The unique identifier and name of the rule.
* `seq`: The sequence number (top-down evaluation order).
* `enabled` / `action`: Whether the rule is active (`True`/`False`) and its decision (`permit`/`deny`).
* `src_zone` / `dst_zone`: Security zones of source and destination.
* `src_iface` / `dst_iface`: Input and output network interfaces.
* `src_addr` / `dst_addr`: Source and destination IP addresses/subnets (anonymized via RFC 6235).
* `src_addr_negated` / `dst_addr_negated`: Boolean flags indicating if the addresses are negated.
* `src_port` / `dst_port`: Source and destination port numbers/ranges.
* `src_port_negated` / `dst_port_negated`: Boolean flags indicating if the ports are negated.
* `protocol` / `service`: IP protocol numbers and mapped service names.
* `ip_version` / `app_id` / `user_id`: IP version (IPv4/IPv6), NGFW Application ID, and NGFW User ID.

### Anomaly Status and Audit Columns
* `anomaly_status`: Evaluates to `clean` (no findings involve this rule) or `affected` (at least one anomaly involves this rule).
* `anomaly_count`: The total number of findings in which this rule participates.
* `anomaly_types`: Pipeline-delimited (` | `) list of anomaly classes (e.g., `shadowing`, `redundancy`, `conflict`, `generalization`, `over_permissive`).
* `related_rule_ids` / `related_rule_names` / `related_seqs`: Multi-valued lists mapping the other rules involved in the respective findings.
* `related_roles`: The role of this rule in each finding (e.g., `shadowed`, `redundant`, `earlier`, `later`, `special`, `over_permissive`, `covering (anchor)`, `general (anchor)`).
* `explanations`: Human-readable explanations generated deterministically by the detection engine.
* `overlap_details`: The exact intersection of multi-dimensional spaces `M(Ri) ∩ M(Rj)` that triggered the finding.
* `risk_scores`: The calculated scalar risk score in `[0, 1]` for each associated finding.

## Association Counting and Mathematical Consistency

The main results file (`results/anomalies.jsonl`) contains exactly **1,387 unique findings**:
* **Shadowing**: 149 findings
* **Redundancy**: 260 findings
* **Conflict**: 499 findings
* **Generalization**: 343 findings
* **Over-permissive**: 136 findings

When these findings are mapped rule-by-rule, the total number of rule-finding associations in `all_rules_status.csv` is exactly **2,257**:
1. **Single-Rule Findings**: `over_permissive` findings involve exactly 1 rule and contribute **136** associations.
2. **Pairwise Findings**: `shadowing`, `redundancy`, and `conflict` involve exactly 2 rules each (e.g., an earlier rule and a later rule), contributing `(149 + 260 + 499) × 2 = 1,816` associations.
3. **Collapsed Generalization Findings**: To prevent redundant reports for reviewers, generalization anomalies sharing near-universal permit-all anchors are collapsed into a single headline finding on the anchor rule side while remaining individually mapped on the specific rules. This optimization reduces the representation in the status files to exactly **305** associations.

Thus, `136 + 1,816 + 305 = 2,257` total associations. This rigorous structure ensures that peer reviewers can audit every single rule and its complete context of associations without information loss.

## Finding Verification and Audit Workflow

To verify any reported finding:
1. Open the target vendor's status CSV file (e.g., `fortigate_rule_status.csv`).
2. Search for the rule using its `rule_id` or sequential order (`seq`).
3. Examine `anomaly_types` and `explanations`.
4. Cross-reference `overlap_details` with the rule's matching fields (`src_addr`, `dst_addr`, `src_port`, `dst_port`, `protocol`).
5. Confirm that the overlap mathematically exists and matches the logic described in the explanation.
